# ShiftSwap

A full-stack web application for managing student work shifts and shift-change requests, developed as a Software Engineering II course project.

ShiftSwap brings shift availability, requests, administrator decisions, and task tracking into one interface. The project combines a browser-based frontend with a Node.js API and a SQLite database.

## Features

- **Account access:** Register and sign in with a username and password.
- **Shift dashboard:** Browse available shifts and view personal assignments.
- **Request management:** Submit and respond to shift-change requests, claim open requests, and track request status.
- **Administrator workflow:** Create shifts and approve or reject requests.
- **Task tracking:** View and update to-do items.
- **Persistent storage:** Store users, shifts, requests, and tasks in SQLite.

## Technology Stack

| Layer | Technologies |
| --- | --- |
| Frontend | HTML, CSS, JavaScript |
| Backend | Node.js, Express |
| Database | SQLite through the `sqlite3` package |
| Authentication | JSON Web Tokens and bcrypt password hashing |
| Local development | concurrently, http-server |

## Architecture

The frontend runs on port **8080** and sends HTTP requests to the backend on port **3000**. Protected API routes use a bearer token returned at login. The backend reads and updates `users.db`.

## Run Locally

### Requirements

- Node.js and npm installed on your computer.
- An internet connection for the first dependency installation.
- Ports 3000 and 8080 available.

Use the Node.js version from your working development environment when possible. The `sqlite3` dependency includes a native component, so installation may vary across operating systems and Node.js versions.

### Install and start

From the project root:

```sh
cd Backend-Server
npm ci
npm run dev
```

Open **http://localhost:8080** in your browser. Keep the terminal running during the demonstration. Press **Ctrl+C** to stop the servers.

For later sessions, run `npm run dev` from `Backend-Server`; there is no need to reinstall dependencies each time.

> If your backend folder is named `Backend Server` rather than `Backend-Server`, use `cd "Backend Server"` instead. Keep the frontend folder name `Frontend UI`, as the startup script refers to that path.

### Start the servers separately

If the combined command has a shell-quoting issue, use two terminals, both opened in the backend directory.

Terminal 1:

```sh
npm start
```

Terminal 2:

```sh
npx --no-install http-server "../Frontend UI" -p 8080 -c-1
```

Always start the backend from its own directory because the database path is relative: `./users.db`. Keep this file to preserve the existing demonstration data.

## Local Demonstration

1. Start both servers and open http://localhost:8080.
2. Sign in using an existing account, or register a test account.
3. Browse the dashboard and personal shifts.
4. Submit or respond to a request using the available test data.
5. Use the administrator account to explore shift creation and request decisions.

After dependency installation on macOS, local startup, database connection, logout/login, and request operations were manually confirmed. This is a smoke check, not a complete automated test suite.

## Troubleshooting

- **`Cannot GET /` at port 3000:** Expected. The backend provides API endpoints but does not define a homepage. Use port 8080 for the interface.
- **`favicon.ico` returns 404:** The browser tab icon is missing; this does not affect the shift-management workflow.
- **Login or requests stop working:** Keep the backend running and sign in again if the session token has expired.
- **Native dependency installation fails:** Check Node.js compatibility and the local build environment; prefer the environment in which the project previously ran successfully.

## Repository Notes

`node_modules` is generated by `npm ci` and is intentionally excluded from the repository. The dependency manifests remain included. If uploading through the GitHub website, manually exclude `node_modules`; `.gitignore` does not filter files selected for a browser upload.

This is an academic prototype for local demonstration. It retains development authentication settings and has dependency audit warnings; it is not presented as a production deployment. Use non-sensitive demonstration data when publishing the database. Hosting the source code on GitHub does not run the backend service.
